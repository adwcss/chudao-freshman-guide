# 新生指南：接手评估与实施顺序

核查日期：2026-10-08。依据：用户提供的赛事要求、交接指南及项目压缩包。

## 1. 本轮结论与范围

项目已有校园新生问答和地图两条功能线，适合继续完善。当前最应先解决的是可迁移运行、资料时效与引用可靠性、真实演进记录。对话上下文、混合检索和办事清单可在这三个基础上推进。

用户本轮请求是先阅读接手文件、理解赛事要求。交接文档中的操作命令与优化路线是原作者建议，需要经过代码核查再采用；其中“必须放在 D 盘”、补建旧开发历史、直接冻结原虚拟环境等建议不能直接当成实施依据。

本轮已完成源码接收、静态检查和本地切分验证，应用业务代码保持接收时内容。新增的是核查脚本、脱敏材料副本、接收清单及本评估。没有启动前后端、下载模型、调用交接密钥或重建向量库。因此，“已能跑”目前仍是交接方陈述，全链路运行需要后续验收。

## 4. 已确认的问题

| 优先级 | 问题与证据 | 影响与处理 |
|---|---|---|
| P0 | 缺失原开发 Git 和对话记录 | 向原作者收集已有真实证据；从接手时点记录真实新增改动与核查过程 |
| P0 | `frontend/app.py:34` 将地图写死为 D 盘路径；后端地址也固定为 localhost | 地图和服务配置按项目位置/环境变量读取，验证不同目录启动 |
| P0 | `splitter.py:96` 起的 Markdown 切分跳过一级标题开头的整段 | 来源网址、第三方标签和年份提示可能随文档头一起丢失，需要继承为每块元数据 |
| P0 | 补充入学指南的 chunk 保留“2024级”，却丢失文档头“2024级参考信息”和来源链接 | 对当年安排应按适用年份检索、标明历史参考；采集日期不能充当内容适用日期 |
| P1 | 校园地图免责声明位于没有三级标题的部分，当前切分结果不含“地图为示意” | 地图识别内容应带来源类型与不确定性，必要时人工校对 |
| P1 | `frontend/app.py:617` 用路线标题调用地点接口，后端统一追加“在哪?” | 用户看到“学校在哪些站点安排接站?”，实际检索“接站在哪?”；改成发送完整问题 |
| P1 | 请求只传 `question`，模型只接收 system/user 两条消息 | 页面能显示历史，但“那学费呢”这类追问没有会话上下文 |
| P1 | `chat_service.py:143` 的检索调用在大模型异常处理之外 | 向量库/检索故障不在该兜底分支覆盖范围内，应单独处理 |
| P1 | `is_relevant` 仅用最接近的一个 chunk 判断，后续上下文却包含全部 top 8 | 一个相关结果可能使其他弱相关结果一起进入模型，需筛选并用问答集验证阈值 |
| P1 | 导入向量库模块时即创建 embedding 函数；依赖仅设置最低版本 | 冷启动可能受模型缓存和网络影响，需实测安装、模型准备与启动时间 |

交接指南声称 `ingest.py` 的资料目录也是硬编码，经核查并非如此：`backend/scripts/ingest.py:25` 已由 `__file__` 推导项目根目录。没有必要重复修改这一处。

“流式回答带引用”已经存在实现，但现在附的是检索结果列表；尚未验证模型正文中的每项断言都被引用支持。文档宣称“FAQ 全覆盖”同样需要运行问答评测来证明。

## 5. 真实演进记录的处理

交接指南建议把已有功能拆成多个提交来补历史。这会把接收时已经存在的代码混淆为新发生的开发，应改为明确记录“收到现有实现的基线”，注明原作者与证据缺口。

后续每一轮实际变更对应需求、真实 AI 对话、代码差异、验证结果与提交。原作者已有的导出记录、录屏和仓库日志按原始来源保存，不倒填日期、不编写不存在的对话。基线快照不能替代原始演进链，也不能自动证明满足赛事的原创与历史要求。

本轮的 `received-baseline.json` 记录原包哈希及各文件哈希，`intake-check.json` 记录本地验证。它们证明收到什么、检查到什么；后续的真实功能迭代从这个时间点开始。

## 6. 建议实施顺序与验收

### 第一批：可运行与可追溯的基础

1. 整理代码来源、原作者授权和已有演进材料；建立独立项目仓库并保留真实接收基线。
2. 配置地图路径、后端地址及环境变量模板，建立新虚拟环境与经过验证的依赖方案。
3. 实测启动、模型准备、入库与重启，完成正式 README；记录冷启动时间，验证十分钟重现目标。
4. 修正路线按钮发送的问题，验收四步路线和八个地点入口。

验收：在非 D 盘项目目录运行，健康接口与统计接口可用，地图可显示；密钥不进入仓库；路线显示的问题与发送的问题一致。

### 第二批：可信问答

1. 让每个 chunk 继承来源链接、来源类别、适用年份与采集日期。
2. 更新并核对当年官方迎新资料；历史信息和第三方建议有明确展示规则。
3. 建立小型问答评测集，覆盖 FAQ、陌生问题、年份冲突、无答案和断流/检索故障。
4. 接入有限长度的多轮上下文，验证追问指代和当前问题的检索。
5. 根据评测决定是否引入中文关键词与向量混合检索，记录改进前后的实际结果。

验收：追问能接上上一轮；历史报到日期不会被当作当年通知；可追溯到真实资料；无答案和故障有清楚提示。

### 第三批：产品闭环与参赛交付

1. 由已有资料生成可勾选的报到材料/手续清单，帮助新生从查询推进到准备完成。
2. 按真实使用反馈完善首屏、响应状态、来源阅读和地图交互。
3. 从实际开发中选取至少三个完整核心迭代的 AI 对话链；制作演示视频与技术 PDF。
4. 完成干净环境重现、材料检查和评审访问方案。

Docker、embedding 更换、重排模型、多模态及多 Agent 属于后续可选路线，先通过运行和问答评测确认收益，再决定采用。

## 7. 本轮核查的重现方式

在项目根目录执行：

```powershell
python -X utf8 -I -S tools/inspect_handover.py --output docs/intake-check.json
```

只需要 Python 标准库。脚本解析源码、运行已核查的纯文本切分器，并以只读模式查看接收数据库；不依赖 DeepSeek 密钥、Chroma 安装或 embedding 模型下载。此核查不是应用运行验收。
